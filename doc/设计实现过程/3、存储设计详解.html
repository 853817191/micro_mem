①存储选型过程（为什么这么存）

从"要检索"出发，选引擎、再抽象成接口——底层一次定死，但留可插拔的口子。

图 1 · 存储选型与多数据源架构
▼需求：网要能快速检索（关键词 / 语义 / 图遍历）
选型评估（6 引擎） SQLite 全覆盖 ✓ | DuckDB 向量弱 | Neo4j 太重 | LanceDB/Chroma 图弱 | 纯文件能力有限
▼选定
SQLite 为默认实现 零部署单文件 · FTS5 全文 · sqlite-vec 向量 · 递归 CTE 图遍历
▼但要求"可换引擎"——抽象成接口
NetworkStore 接口 构建：rebuild / upsert
检索：query / traverse / semantic
⇄
SqliteNetworkStore 默认实现 · 5 张表
Neo4jNetworkStore 可选 · 配置切换
MemoryNetworkStore 内存实现 · 测试用
▼config 决定用哪个：network_store: sqlite

选型要点

  • 底层一次定死：真值 = Markdown 文件；网 = NetworkStore 接口；默认实现 = SQLite；工具层 = Python。
  • 契约定死、实现开放：换引擎 = 新写一个实现类 + 改配置，上层不动，真值无损（网可重建）。
  • 五张表是 SqliteNetworkStore 的内部结构——换 Neo4j 时，这五张表不存在，由图库替代，但接口签名不变。

②五张表详解（SqliteNetworkStore 内部）

一张"节点表"存知识本体，四张"辅助表"分别支撑：全文、语义、关系、外部引用。

图 2 · 五张表及关联关系
nodes 节点表 知识本体（真值副本）
nodes_fts 全文索引 FTS5 倒排 · 关键词字面检索
nodes_vec 向量索引 sqlite-vec · 模糊提示词语义检索
edges 边表 网的关系 · 图遍历
external_refs 外部锚点 需求单号 / MR / UAT
nodes_fts / nodes_vec 用 rowid 关联 nodes · edges / external_refs 用 id 关联 nodes

每张表的作用与字段

表存什么解决什么查询关键点
nodes id · file · title · summary · type · scope · status · created/updated 按 id 取节点、按 type/scope 过滤、取摘要判断 summary = 判断用摘要（确认"是不是这件事"，不读全文）；无 body——全文只在 md 文件，下钻按 file 读
nodes_fts 倒排索引 + 内容（title + body，rebuild 时从 md 读入） 关键词字面检索：搜"审批"命中含"审批"的节点 FTS5 · trigram 中文分词 · 独立表（自存索引；nodes 无 body）
nodes_vec 每条知识的 embedding 向量（float[N]） 语义检索：模糊提示词→向量→最近邻节点 sqlite-vec 虚拟表；向量由 embedding 服务算出后写入
edges from_id · to_id · edge_type（parent / link / trace） 图遍历：父子挂靠、关联引用、溯源回锚点 from/to 建索引；递归 CTE 多跳
external_refs node_id · ref_type（idev/mr/uat/url）· ref_value 知识 ↔ 外部真实世界 需求单号、MR 链接、UAT 地址——不是知识本身，是锚点

五张表设计详解（每张表的意义与解决的问题）

表意义（一句话）解决的问题关键机制
nodes 知识本体的索引化身 按 id/type/scope 定位知识、取 summary 判断 rowid 是四表关联键；无 body（正文只在 md，避免双份同步）；summary = 判断用摘要（title 扫 → summary 判 → file 钻）
nodes_fts 字面检索（关键词） 搜标题词 + 搜正文细节 title 与 body 是独立内容源（body 不含标题短语），都索引才两路可搜；trigram 解决中文子串匹配（默认分词对中文整段切）；FTS5 独立表（UPDATE 用 delete+insert）；rowid 关联 nodes
nodes_vec 语义检索（模糊提示词） 一句话 / 同义表达 / 语义相关——FTS 字面抓不到的 embedding：文本→向量，语义近则距离近；向量输入用 summary（知识精华）；embedding 是外部服务；与 FTS 双路召回 + RRF 合并（双路命中者优先）
edges 网的关系 图遍历：由一件事串联相关事 edge_type：parent（挂靠）/ link（关联）/ trace（溯源）；从 frontmatter parents/links 重建；递归 CTE 多跳
external_refs 知识 ↔ 真实世界的桥 从知识跳到需求单号 / MR / UAT / URL，落地实际操作 ref_type：idev / mr / uat / url；与 edges 区别（内部关系 vs 外部锚）、与 file 区别（库内真值 vs 库外工单）；一对多、可变化

三个横切机制

  • rowid 关联：FTS / vec 用 rowid（物理键）关联 nodes；nodes.id（k-0003）是业务键，供 edges / external_refs 引用
  • 双路召回：FTS（字面）+ 向量（语义）各自召回 → rowid 并集去重 → RRF 排序 → 图扩展 → 模型读 summary 判断
  • 三级粒度：title 扫（候选列表）→ summary 判（是不是这件事）→ file/锚点 钻（细节与原文）

建表 SQL（实际可执行）

-- ============================================
-- 记忆/知识管理系统 · SqliteNetworkStore 完整表结构
-- ============================================

-- ① 节点表：每个节点 = 一条知识（真值在 md 文件，此处为可重建副本；无 body）
CREATE TABLE IF NOT EXISTS nodes (
  id      TEXT PRIMARY KEY,                              -- 知识唯一标识：k-0003
  file    TEXT NOT NULL,                                 -- 指向 md 真值：knowledge/k-0003_xxx.md
  title   TEXT NOT NULL,                                 -- 标题（候选列表一眼扫）
  summary TEXT,                                          -- 判断用摘要（确认"是不是这件事"，不读全文）
  type    TEXT NOT NULL CHECK (type IN ('event','model','fact','method')),
                                                        -- 认识论类型
  scope   TEXT NOT NULL CHECK (scope IN ('universal','domain','personal')),
                                                        -- 成立范围
  status  TEXT NOT NULL DEFAULT 'draft'
          CHECK (status IN ('draft','evolving','settled','deprecated')),
                                                        -- 成熟度
  created TEXT,                                          -- 创建时间
  updated TEXT                                           -- 更新时间
);

-- ② 全文索引：关键词字面检索（FTS5 独立表：自存倒排+内容，rebuild 时从 md 读正文喂入）
CREATE VIRTUAL TABLE IF NOT EXISTS nodes_fts USING fts5(
  title, body,
  tokenize = 'trigram'         -- 中文子串匹配：搜"需求"命中"需求单"
);

-- ③ 向量索引：模糊提示词语义检索（sqlite-vec，N = embedding 维度，如 768）
CREATE VIRTUAL TABLE IF NOT EXISTS nodes_vec USING vec0(
  embedding float[N]
);

-- ④ 边表：网的关系（挂靠/关联/溯源）
CREATE TABLE IF NOT EXISTS edges (
  from_id   TEXT NOT NULL REFERENCES nodes(id),
  to_id     TEXT NOT NULL REFERENCES nodes(id),
  edge_type TEXT NOT NULL CHECK (edge_type IN ('parent','link','trace')),
  PRIMARY KEY (from_id, to_id, edge_type)
);
CREATE INDEX IF NOT EXISTS idx_edges_from ON edges(from_id);
CREATE INDEX IF NOT EXISTS idx_edges_to   ON edges(to_id);

-- ⑤ 外部锚点：知识 ↔ 外部真实世界（需求单号/MR/UAT/URL）
CREATE TABLE IF NOT EXISTS external_refs (
  node_id   TEXT NOT NULL REFERENCES nodes(id),
  ref_type  TEXT NOT NULL CHECK (ref_type IN ('idev','mr','uat','url')),
  ref_value TEXT NOT NULL,
  PRIMARY KEY (node_id, ref_type, ref_value)
);

不管知识来自蒸馏还是收录，都先落成 Markdown 真值文件，再从文件重建/增量写入五张表。

入口 B：收录 你主动告知 → 知识

正文：业务流程（顺序在正文）

有 md 文件 vs 没有 md 文件

情况怎么处理
有 md 文件的知识
主通道		 md 文件是真值，五张表是可重建索引。rebuild 时从文件读入全部重建；文件丢了知识才丢，库坏了重建即恢复。
没有 md 文件的知识
例外		 设计原则：一律先补落 md 文件（用户直接说"记住这个" → 先生成文件再走同一管道）。因为真值必须人可读、可 review，纯 DB 节点会失去这一保证。若未来确有纯运行时知识，可支持 file 为空的节点（此时 DB 即真值），但非主路径。
为什么统一落文件？——① 你能 review 每条知识；② 文件可 git 版本管理；③ 索引重建有唯一真值源。这正是"真值一次定死"的体现。

④如何检索（完整场景）

一条提示词，系统走"精确 + 语义"双路召回 → 拿 node id → 沿网扩展 → 模型读摘要判断（不读全文）。

图 4 · 检索链路（以"改一下审批环节"为例）
提示词："改一下审批环节"
精确路：FTS5 MATCH '审批' → rowid 命中
语义路：向量 提示词→embedding → nodes_vec 最近邻
▼双路结果合并 → nodes 拿节点（领导审批环节 k-0010）
沿 edges 图遍历 挂靠：父（需求单流程）
关联：代码（审批 Controller）
关联：方法（审批流配置方法）
▼返回候选（id/title/summary/file/type/scope）→ 大模型读 summary 判断是不是这件事（不读全文）
需要细节 → 按 file 读 md 全文 → 下钻锚点（原始记录）→ 回对原文

检索的 SQL（系统机械执行）

-- 精确路：关键词（FTS5，trigram 支持中文子串）——只取轻量字段，不取 body
SELECT n.id, n.title, n.summary, n.type, n.scope, n.file
FROM nodes n
WHERE n.rowid IN (
  SELECT rowid FROM nodes_fts WHERE nodes_fts MATCH '审批'
)
AND n.type='fact' AND n.scope='domain'        -- 可叠加过滤
ORDER BY rank LIMIT 10;

-- 语义路：模糊提示词（向量最近邻）
SELECT n.id, n.title, n.summary, n.file, v.distance
FROM nodes_vec v JOIN nodes n ON n.rowid = v.rowid
WHERE v.embedding MATCH :prompt_vec            -- :prompt_vec 由 embedding 服务算出
ORDER BY v.distance LIMIT 10;

-- 图遍历：从节点沿边扩展（递归 CTE，2 跳）
WITH RECURSIVE reach(from_id, depth) AS (
  SELECT 'k-0010', 0
  UNION ALL
  SELECT e.to_id, r.depth+1 FROM reach r
  JOIN edges e ON e.from_id = r.from_id
  WHERE r.depth < 2
)
SELECT * FROM reach;

链路 = 索引命中（关键词/语义）→ node id → 图扩展 → 模型读 summary 判断 → 确认后按 file 下钻 md/锚点原文。检索归系统（机械），判断归模型（读摘要），锚归原文。三级粒度：title 扫 → summary 判 → file/锚点 钻。

⑤蒸馏后数据如何更新

新知识产生 = 增量 upsert；已有知识改版 = 更新该节点 + 重建它的索引与边。

图 5 · 更新流程（增量，非全量）
新知识（蒸馏/收录） 生成新 md → upsertNode → upsertEdge
知识改版（流程变了） 改 md → 更新 nodes + 重建该节点 fts/vec + 更新 edges
▼全量重建（rebuild）只在需要时跑——如首次、或手动修复

更新要点

  • 增量优先：蒸馏/收录产生一条知识，只 upsert 这一条 + 它的边，不重建全库。
  • 改版走"成熟度"：流程"短期确定、长期演进"——改版时旧内容留痕（status: deprecated），新版本落新内容，索引同步重建。
  • 可重建兜底：任何时刻索引出错，跑一次 main.py rebuild 从 md 文件全量恢复，真值无损。
