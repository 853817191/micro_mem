记忆 / 知识管理系统 · 快速上手

让 AI 把「对话」沉淀成「知识」，并在下一次遇到相似问题时自动关联、复用，越用越懂。

新手阅读本页，约 15 分钟 · 建议按 ①→④ 顺序阅读

①一句话骨架

先记住这一句话，后面所有内容都是它的展开：

系统 = 一个锚点 ＋ 四类知识 ＋ 一张网，由四类操作驱动，形成「沉淀 → 关联 → 复用 → 再沉淀」的闭环。
图 1 · 一句话骨架
锚点 Anchor 对话记录（保真、可溯源）
知识 Knowledge 事件 / 领域 / 方法 / 常识（type × scope）
网 Network 关联（把知识串起来）
四个操作驱动
记忆 蒸馏 收录 关联
沉淀→关联→复用→再沉淀

展开解读

  • 锚点 每次聊天的完整原始记录，原样保存、不改动。它是一切知识的"根"——任何抽象出来的东西都能回溯到它，所以它也是纠错和可信的最终依据（"权威是原文"）。
  • 知识 从对话中提炼出来的、或你主动告诉 AI 的可复用内容。不是一条条的聊天记录，而是"发生过什么 / 是什么系统 / 怎么办 / 是什么"这类真正有价值的东西。
  • 网 知识不是孤立的——事件、方法、常识之间通过关联互相连接，由一件事可以牵出相关的事。网管"谁连谁"，具体语义放在知识内容里。
  • 四操作 是让系统转起来的四个动作：记忆（存原话）、蒸馏（提炼知识）、收录（你告知）、关联（建立连接）。
一句话本质：这不是一个"聊天记录备份"系统，而是一个"把对话变成可复用经验"的系统。锚点负责保真，知识负责价值，网负责串联。

②整体架构（四层）

系统从下到上分四层，数据从「输入」流向「存储」，再被「复用」层取出来干活。

图 2 · 四层架构与数据流转
输入层
每次对话你主动告知（流程 / 方案 / 事实）
↓记忆 / 收录
操作层
记忆→ 蒸馏→ 收录→ 关联
↓写入
存储层
锚点 · 对话记录 知识 · 事件/领域/方法/常识 网 · 关联边
↑调出 / 下钻
复用层
检索（沿网找到旧知识）→ 复用（讲当时怎么做的）→ 修订（按新情况调整）→ 再沉淀（写回存储层）

各层职责

层职责关键点
输入层知识的来源：对话自动产生 / 你主动告知两种输入管道，来源不同，处理方式不同
操作层对输入做加工：四类操作决定"怎么进系统"记忆全自动；蒸馏第一阶段手动；收录你说了才算；关联自动为主
存储层知识的存放：锚点 / 知识 / 网三个角色锚点保真，知识提炼，网串接
复用层知识的使用：遇到新问题，取旧知识来帮忙（CBR 闭环）检索 → 复用 → 修订 → 再沉淀，一次循环让网更密

层之间如何流转

  1. 输入 → 存储：对话走记忆（每次结束自动落盘成锚点）；你主动告知走收录（直接变成知识）。
  2. 存储内加工：锚点经过蒸馏变成知识；知识之间通过关联挂进网。
  3. 存储 → 复用：新问题来时，复用层沿网检索，从知识下钻到锚点细节。
  4. 复用 → 存储：这次解决过程再沉淀回存储层，网更密、知识更丰富。
四层是逻辑分层，不是四个独立系统——一个会话可能同时在操作层（蒸馏）和存储层（落盘）产生动作。

③数据模型

系统里只存三样东西：锚点、知识、网。知识的核心是「内容 + 来源 + 类型 + 范围」四个维度。

图 3 · 数据模型（三个实体的字段）
锚点 Anchor
content : 完整对话原文 特点：保真 · 不可变 · 可溯源
对应存储：Layer 0/1（原始 JSONL / 可读归档）
知识 Knowledge
content : 知识本身（因类型而异） sources : List<Source>（可扩展接口） type : EVENT | MODEL | METHOD | FACT scope : UNIVERSAL | DOMAIN | PERSONAL parent : 可挂靠多个父节点（DAG）
网 Network
节点 = 知识 边 = 挂靠（父子）· 关联（引用）· 溯源（回锚点） 原则：网管结构（谁连谁），内容管语义（顺序/逻辑在内容里）

一句话记法：事件 = 发生了什么，领域 = 这是什么系统，方法 = 怎么办，常识 = 是什么（普世），共识 = 是什么（项目组内）。新差异 = 加维度值，而不是无限加类别。

来源（Source）—— 可扩展接口

每条知识都带着自己的来源，来源不是写死的枚举，而是可扩展的接口：

来源含义例子
ConversationDistilled从对话蒸馏提炼出来的"需求单流程"是你在讨论中确认的
UserDeclared你主动告知的你说"记住，发布走 UAT→PRE→生产"
……（将来可加）报告导入、文档导入等从历史排障报告导入经验

一条知识可以同时有多个来源——比如一个经验先由对话蒸馏产生，后来你又主动告知补充过，两个来源共存。

每一步的触发时机

步骤什么时候发生谁触发
② 记忆每次会话结束全自动，无需你操作
③ 蒸馏你主动说"帮我蒸馏"（第一阶段）你手动触发；自动化是后续目标
③ 收录你主动告知一个方案 / 流程 / 事实你手动触发
④ 关联蒸馏 / 收录时自动找相似内容建边，也可手动补自动为主 + 手动补
⑤ 复用下一次提出相似需求 / 问题时系统自动沿网检索
第一阶段刻意保持手动蒸馏——先验证蒸馏产出质量，再谈自动化。系统对"沉淀了什么"保持可控。

⑤ 一个完整例子（需求单场景走一遍）

把前面四张图串起来：用你最熟悉的"需求单"业务看全流程。

第一次：收录业务流程（一次，永久生效）

  1. 你告诉 AI："需求单业务流程是：用户提交需求单 → 服务商报价 → 领导审批 → 客户选方案 → 供应商出票，里面有很多细节。"
  2. 收录触发 → 生成一条知识： 类型=MODEL · 范围=DOMAIN（领域模型）· 来源=UserDeclared · 内容=需求单业务流程
  3. 流程是层级结构：总流程是父知识，每个环节（提交/报价/审批/选方案/出票）是子知识，挂靠在父知识下面；执行顺序写在父知识内容里（①提交→②报价→③审批→…）。
  4. 每个环节节点关联到对应代码（如"领导审批"→审批相关 Controller），形成"业务环节 ↔ 代码"的关联。

第二次：下次说"改需求单"（复用闭环）

  1. 你新建一个会话，说："我要改需求单相关的需求。"
  2. 系统沿网找到〔需求单业务流程〕共识节点 → 你指"我想改『领导审批』环节" → 定位到环节细节 → 沿关联下钻到审批相关代码。
  3. AI 结合上次的开发经验（方法：用 AI 做需求开发的标准流程）和锚点里的细节，直接进入讨论，不用你再讲一遍流程。
  4. 开发完成后，这次过程再沉淀成新的"事件"，挂回需求单主题 → 网更密。
对比你现在的痛点："每次都要重新讲一遍流程"被彻底消除——因为流程已经作为共识沉淀在网里，下次自动关联。

常识 Common Sensetype=FACT × scope=UNIVERSAL，普世事实
共识 Consensustype=FACT/METHOD × scope=DOMAIN，项目组内达成的一致认知（代码、约定、规则）
