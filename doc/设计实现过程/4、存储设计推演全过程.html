②逐阶段推演（完整对话记录）

阶段 1
设计方法论 · 螺旋迭代，但底层一次定死
确定"怎么设计"——业务层螺旋、底层选型不试错
👤 用户我想采用螺旋迭代的方式做设计：先做基础数据模型，用实际场景验证存储，再设计复用，发现问题再优化存储，再验证。提出螺旋
👤 用户螺旋迭代是针对业务的，这种底层的，我不建议用螺旋迭代，如果变动，影响面比较大。底层不迭代
🤖 AI区分"真值 vs 索引"：真值（Markdown 格式）影响面大、一次定死；网是可重建的索引，换引擎影响面被隔离。真正不能变的是真值格式。影响面隔离
对齐：业务层螺旋迭代（场景驱动）；底层一次定死（真值影响面大）。
阶段 2
存储形态 · 结构化还是非结构化？
从"二选一"到"按数据性质分配"，并由第一原则驱动
👤 用户我们使用结构化存储好，还是非结构化存储？根本选型
🤖 AI不是二选一，是按数据性质分配：内容（锚点/知识正文）→ 文件非结构化；元数据（type/scope/sources）→ frontmatter 结构化；关系（网）→ 结构化。理由：你要 review（人读）、Claude Code 读文件（AI 读）、复用要图遍历（机查）。混合分配
👤 用户再回到最开始的观点：要让 AI 正确想起某件事，是系统检索，大模型判断。拉回第一原则
🤖 AI第一原则恰好决定存储分配——谁消费决定谁用什么存储：系统消费的网 → 结构化（机械检索的落点）；模型/人消费的知识、锚点 → 文件。如果网不结构化，系统就没有"机械检索"的落点。原则驱动
对齐：存储形态 = 按数据性质分配 + 由"谁消费"驱动。真值 = 文件；网 = 结构化。
产出：文件真值 + 索引增强的基调。
阶段 3
网引擎选型 · SQLite？接口化？
从"为什么 SQLite"到全选型扫描，再到接口可插拔
👤 用户网为什么要用 SQLite？优势是什么？质疑
🤖 AISQLite 优势：图遍历（递归CTE）/组合查询/约束一致/性能。诚实边界：个人量级性能差异不大，核心在查询复杂度——单跳关联文件够，多跳串联要图库。诚实边界
👤 用户底层的我不建议螺旋迭代……除了 SQLite，还有其他选型吗？全选型扫描
🤖 AI6 引擎评估：SQLite（全覆盖）/ DuckDB（向量弱）/ Neo4j（图强但重）/ LanceDB、Chroma（向量强图弱）/ 纯文件（能力有限）。SQLite（FTS5 + sqlite-vec）唯一单文件零部署全覆盖。选型结论
👤 用户构建网、查询检索网的时候，调用的其实是一个接口，具体是 SQLite 实现还是 Neo4j 实现，可由配置决定。接口化提案
🤖 AI这正是端口-适配器：契约定死、实现开放。NetworkStore 接口 = 构建（rebuild/upsert）+ 检索（query/traverse/semantic）。换实现 = 新类 + 改配置，上层不动。架构确认
对齐：SQLite 默认实现；NetworkStore 接口可插拔（SQLite/Neo4j/Memory）。
阶段 4
实现语言 · 引入 Python
裸 sqlite3 CLI 做不了逻辑，需要脚本语言
👤 用户需要引入一门语言吗？比如 Python，用来跟 SQLite 交互，还是 CLI 工具直接交互？影响大吗？语言选型
🤖 AI需要 Python：裸 sqlite3 CLI 只能查表，做不了重建索引（解析 frontmatter）、向量检索、图遍历这些逻辑。影响可控——你机器已有 Python。封装成统一命令入口 main.py rebuild/search/traverse，Claude Code 只调命令。结论
对齐：工具层 = Python，统一命令入口；sqlite3 CLI 仅调试。
阶段 5
建表 · 五张表初版 + 检索机制
核心问题：节点存什么、关键词怎么快搜
👤 用户SQLite 可以存储我们的网……如何快速检索网上的节点？比如给一个关键词，如何快速搜索出这个关键词所在的节点？表结构 + 检索
🤖 AI五张表：nodes（节点）+ nodes_fts（FTS5 全文）+ nodes_vec（向量）+ edges（网）+ external_refs（外部锚点）。关键词检索 = FTS5 倒排索引，trigram 解决中文分词。表 + FTS
👤 用户如果另外建一个索引表，专门对知识内容做关键词提取，关联 node 主键 id……效率会不会高一点？自建索引想法
🤖 AI你的想法 = FTS5 的架构——它就是"独立倒排索引表 + rowid 关联"，外部内容表模式连正文都不存。不用重复造轮子。澄清 FTS5
👤 用户问题 1 认可，不重复造轮子。2、向量解决了什么问题？是检索出来的数据带权重值吗？问向量
🤖 AI向量不是"带权重"，是"语义召回"——FTS5 找"写了这个词的"，向量找"想表达这个意思的"（搜"内存溢出"命中"OOM 排查"）。代价：需要 embedding 服务。向量澄清
👤 用户用，必须用。拍板向量
对齐：五张表 + FTS5（trigram）+ 向量必上（sqlite-vec）。
阶段 6
Summary 优化 · 判断不读全文
用户提出：检索确认阶段能不能不读 md 文件？
👤 用户检索出很多知识，需要大模型判断确认是不是这件事，这个过程能不能不读 md 文件，将文件内容提取出来一部分，专门用来确认是不是对应的事情？有时候文件会很大。优化提案
🤖 AI可以，而且这正好把两步法的 gist 层落进存储——nodes 加 summary 列，检索返回轻量字段（id/title/summary/file），模型读 summary 判断，确认后才按 file 读全文。三级粒度：title 扫 → summary 判 → file 钻。gist 落地
对齐：summary = 判断用摘要（3~5 句），写在 frontmatter，检索返回轻量字段。
阶段 7
去 body 修正 · 用户发现冗余
"body 只在建索引时用一次，有必要存副本吗？"——这个问题改进了设计
👤 用户node 表里为什么需要一个 Body 字段？设计的初衷是什么？质疑 body
🤖 AIbody 的初衷 = 给 FTS5 全文检索提供内容源（倒排索引需要文本）。没有 body，FTS 没内容可索引。解释
👤 用户那能在建立 nodes_fts 时才用一次，建完索引后 body 是不是就不需要了？有必要存副本吗？发现冗余
🤖 AI你说得对——body 副本是冗余的。正文只在建索引那一刻喂给 FTS5，来源应该是 md 文件，不必常驻 nodes。修正：nodes 去 body；FTS5 改独立表（rebuild 时从 md 读正文喂入）。确认修正
对齐：正文只在 md 文件一处（真值唯一），FTS 索引 rebuild 时从 md 读入——消除双份同步问题。
阶段 8
深度打磨 · 五张表机制逐个讲透
追问每个细节：FTS 生命周期、字段意义、rowid 关联、向量配合、external_refs
👤 用户nodes_fts 在真实的流程中，他的创建或更新逻辑是什么？FTS 生命周期
🤖 AI三个时机：rebuild（全量，扫 md 重插）、upsert（增量单条）、改版（FTS5 不支持 UPDATE，用 delete + insert）。正文每次从 md 读，rowid 对齐两表。机制
👤 用户nodes_fts 表字段，是按照 sqlite 要求一定是这俩字段吗？问字段约束
🤖 AI不是强制的，是我特意设计的——FTS5 列可任意数量任意命名。选 title+body 是因为：title 覆盖标题词、body 覆盖正文细节（两个独立内容源）。trigram 是分词器选项（解决中文子串匹配）。设计意图
👤 用户那从 fts 搜索出来的关键词是怎么跟 node 对应上的？rowid 关联
🤖 AI靠 rowid——FTS5 倒排索引存"词→rowid 列表"，检索返回 rowid，JOIN nodes 对齐。nodes 有双键：id（业务）/rowid（物理）。机制
👤 用户但是我没看到 fts 表里面涉及 rowid 这个字段啊。质疑
🤖 AI对——rowid 是隐式列，不用也不能写在 CREATE（是保留名）。在使用时出现：INSERT 指定、SELECT 取出、JOIN 对齐。隐式机制
👤 用户summary 感觉不应该放在 fts 表里面吧，会数据重复吧。抓重复
🤖 AI你抓得对，收回我上一轮"summary 进 FTS"的建议——summary 是 body 提炼，词已在 body；它只做"返回判断"不做"被检索"。FTS 列保持 title+body。收回
👤 用户有 body 了为什么还需要 title？追问
🤖 AI因为 title 和 body 是独立内容源——正文里通常没有标题短语。搜"需求单业务流程"（完整标题）只有 title 能命中；搜"审批条件"（细节）只有 body 能命中。解释
👤 用户向量表跟 fts 表是怎么配合使用的？问配合
🤖 AI双路召回 + 合并：FTS（字面）+ 向量（语义）各自召回 → rowid 并集去重 → RRF 排序（双路命中者优先）→ 图扩展 → 模型读 summary 判断。机制
👤 用户external_refs 这个呢？问外部锚点
🤖 AI知识↔真实世界的桥：需求单号 / MR / UAT / URL。让记忆里的知识能跳回真实工单落地实际操作；与 edges（内部关系）、file（库内真值）区分。解释
对齐：五张表机制全部讲透（FTS 生命周期 / title+body / rowid 隐式 / 双路召回 / external_refs 桥），并修正了"summary 进 FTS"的错误建议。
阶段 9
场景验证 · 三场景全覆盖
用问题定义阶段的三个实际场景，验证表结构能否存下、能否支撑使用
👤 用户现在阶段二的表结构设计算是完成了，接下来是验证阶段，我们之前验证的三个实际场景，如果用这套表结构来存储，是否能满足，逐个验证。验证指令
🤖 AI逐个走一遍：场景 1（本对话）→ parents 挂靠 + sources 接口 ✓；场景 2（需求开发）→ type×scope + external_refs ✓；场景 3（需求单流程）→ 父 content 顺序 + links 代码关联 + status 成熟度 ✓。三个场景全覆盖，无一表达不了。诚实暴露 3 个小点：review 状态粗细、代码位置承载、顺序检索需解析父 content。验证结论
对齐：五张表 + frontmatter 规范经受住三个真实场景验证。3 个小点（够用但不够细）留待属性设计处理。
产出：《存储设计详解》HTML 完整版 + schema.sql + 本文档。
