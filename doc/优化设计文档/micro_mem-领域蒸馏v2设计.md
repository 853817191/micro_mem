## 一、背景：旧蒸馏为什么不精准（实证）

蒸馏链路 = `mem distill`（系统出增量轮次）→ AI 写 candidates.json（系统外）→ `mem confirm`（落库）。
"判断归模型"原则不变，但旧形态下判断的**供给、约束、反馈**三层全部缺位：

| # | 实锤 | 证据 | 根因 |
|---|---|---|---|
| E2 | **平行树**：k-0016 与 k-0022 同为「国际机票需求单领域」根节点（k-0022 另带 13 个子节点），事后人工 deprecate | data/knowledge/ 两同名 md | 蒸馏第一步是"提炼"而非"定位"；系统不供给已有树，去重靠 AI 自觉 search；幂等条件（同 title + sources 交集）对跨会话重复**必然穿透** |
| E3 | **3MB 怼脸**：真实锚点 490KB~3MB，distill 全文无截断输出，"整体上下文"仅前 8000 字符 | data/anchors/ 实际文件；cli.py 旧 cmd_distill | AI 必然跳读 → 漏信息、抓错重点，review 方也无法对着 3MB 核对完整性 |
| E4 | **审查失效**：候选 = 14 条完整成稿（每条数百字），结构错误（该 edit 却新建）在成稿中隐形，发现时正文已全写完 | data/temp/candidates.json（9-30 批次） | 没有"计划"中间层：定位决策与内容生产耦合成一步，审查对象错位 |

**根因一句话**：旧形态是"单轮批处理 + 软约束 + 零反馈"——把所有判断压给 AI 一口气完成，规则全靠自觉，失误无从回流。
**解法一句话**：把蒸馏从"一口气产成稿"改为"**先对齐结构，再生产内容**"的多轮协议，能机械检查的全部下沉为系统硬约束。

## 二、设计目标（从消费场景反推，场景即验收标准）

| 场景 | 消费者 | 要求 |
|---|---|---|
| A · 接手指导 | 新同事 | 记忆系统可当"领域专家"：领域全貌可导航、可下钻 |
| B · 需求实现 | AI | 拿到需求描述 → 能回答五问：**① 落在哪个领域/环节 ② 现状（入口/接口/表/状态）③ 改动点 ④ 影响面 ⑤ 坑与约束** |

**核心约束（用户拍板）**：代码会变，业务流程与业务规则不易变 → 蒸馏落「入口与索引」，**具体实现看代码，代码才是事实**。
场景 B 是更严格的那个，作为设计目标。

## 三、目标产物：领域树

### 3.1 形状【已拍板】

```
领域根（type=model，aspect 空，无 parent）
├─ 流程轴（aspect=flow）     ── 业务怎么跑：流程阶段节点（创建/报价/选择/审批/出票…）── 下挂实现细节
├─ 结构轴（aspect=structure）── 数据长什么样：实体与表 / 状态机 / 枚举
├─ 边界轴（aspect=boundary）  ── 跟外界怎么交互：外部调用 / 外部入口 / 集成点（消息·job）
└─ 约束轴（aspect=constraint）── 什么不能破坏：业务规则 / 校验 / 坑
```

- **四轴是正交维度**（时间行为 / 空间数据 / 内外交互 / 规则约束），不是拍脑袋清单；**轴可扩展**：新领域可加自定义轴。
- 树**多层**：流程阶段下可继续挂实现细节；拆分唯一开关 =「可独立检索复用」（能独立被搜到并使用的拆节点，否则并入父 body）。
- 对比旧产物（k-0022 批 14 节点平铺挂根的"灌木"）：切面分类层让树可生长——40 个节点时导航能力不崩。

### 3.2 领域根粒度标准【已拍板】

> **一个领域根 = 一个核心业务单据/聚合的完整生命周期**（需求单、订单、审批单各一棵树）。
> 判别：该对象有自己的状态机与生命周期 → 够格当根；只是别人生命周期里的环节 → 当子节点。

### 3.3 数据结构支撑（D1，已落地）

- `Knowledge.aspect: str`：切面标记。领域根为空；切面节点标自身的轴；叶子节点冗余标注所属轴（检索友好）。
  刻意做成 **str 而非枚举**：值域由规则层约定（config 可配扩展），加轴不改代码。
- `Source.turns: list[int]`：轮次级溯源（知识 → 锚点**第几轮**），蒸馏计划契约的落地依赖。
- 索引侧：nodes 表加 aspect 列（既有库自动迁移）；按轴过滤检索成为可能。
- frontmatter 兼容红线：aspect 为空不落盘，存量知识重写字节不变。

## 四、蒸馏协议：四轮多轮制【已拍板】

### 4.0 总览

```
        [会话驱动] 增量轮次 → 压缩视图 ─┐
                                       ├─→ R1 定位 → R2 审计划 → R3 成型 → R4 confirm
        [主题驱动] 领域盘点报告 ────────┘    （AI）    （用户）     （AI）   （系统）
```

### 4.1 Round 1 · 定位（AI 产出蒸馏计划）

**系统供给**（不靠 AI 自觉 search——E2/E4 的教训）：
- 会话驱动：增量轮次**全量原文**（超预算才触发压缩安全阀：剥 tool_result、截长文；预算 config 可配）
  + 按内容**预检索**的已有相关子树（id/title/aspect/summary/parent——标题包含为主、FTS 为辅，不走假语义）；
- 主题驱动：领域已有树全景（按轴分组）+ 相关锚点清单。

**AI 只做定位判断**：这批素材里哪些有知识？每份知识长在树的哪个坐标（哪根轴、挂谁下）？还是 edit 已有？哪些明确不蒸？
产出 = **蒸馏计划**（契约见 4.5）。**此阶段不产正文**——每条只有一句话 gist。

### 4.2 Round 2 · 计划审查（用户）

用户审的是**结构变更单**而非成稿：蒸什么、长在哪、跳过什么——10 秒级可扫完。
结构错误在此拦截（k-0022 平行树在本轮必然现形：计划里会赫然写着"新建领域根"而库里已有）。
此时正文未写，纠错零浪费。审查动作：批准 / 改坐标 / 增删项。

### 4.3 Round 3 · 成型（AI 逐条写正文）

计划批准后逐条提炼。关键机制：**每条只回读 `source.turns` 标注的轮次原文**——
不再面对全量锚点，上下文聚焦（E3 的结构性解法）。正文写作遵第七章内容规范。

### 4.4 Round 4 · confirm（系统硬校验 + 落库 + 归档）

- 硬校验（拒收级/警告级清单见 6.2）；
- 落库（幂等、溯源含 turns、双源协调沿用现有 KnowledgeService）；
- **计划回写归档**：每项落库结果（created/edited/skipped + 知识 id）写回计划文件，存 `data/plans/`（见 4.6）。

### 4.5 蒸馏计划契约【已拍板】

```json
{
  "plan_id": "plan-20261001-001",
  "driver": "session | topic",
  "mode": "domain",
  "domain_root": {"action": "existing", "id": "k-0022"},
  "anchor": "s-20260930-001",
  "items": [
    {"action": "create", "aspect": "flow", "parent": "k-0040",
     "title": "创建需求单流程",
     "gist": "init→checkUserCard→createOrUpdate，提交(RP)才通知供应商报价",
     "source": {"anchor": "s-20260930-001", "turns": [5, 6]}},
    {"action": "edit", "edit_id": "k-0024",
     "gist": "状态机补充 PT/PY 部分出票两态",
     "source": {"anchor": "s-20260930-001", "turns": [9]}},
    {"action": "skip", "gist": "turn 12-15 为环境调试，无领域知识",
     "source": {"anchor": "s-20260930-001", "turns": [12, 13, 14, 15]}}
  ]
}
```

> **driver × mode 是两个正交维度**：driver = 数据从哪来（session 会话驱动 / topic 主题驱动）；
> mode = 蒸成什么形态（domain 领域 / event 事件——event 为未来模式预留，本期不实现）。
> 首版即拆成两个字段：现在拆是一行的事，等事件蒸馏落地再拆要迁移全部存量计划文件。
>
> `domain_root.action=create` 时根的完整内容（title/summary/body）直接放该字段内；
> items 里新建子节点的 `parent` 写 `"$ROOT"` 占位，confirm 先落根得到真实 id 再替换
> （旧流程 MAIN 两段式 hack 的正式化收编：显式、只在新建根时出现、经计划审查）。

| 字段 | 回答 | 治的病 |
|---|---|---|
| `action: create/edit/skip` | 素材的命运（蒸馏判断的全集就这三种） | — |
| `edit_id` | edit 谁 | E2：重复主题走 edit 而非新建，且暴露在审查面 |
| `aspect` + `parent` | 树的坐标（哪轴、挂谁） | 灌木平铺：位置先于内容确定 |
| `gist` | 一句话内容概要 | 审查成本：变更单级，非成稿级 |
| `source.turns` | 来自哪几轮 | R3 聚焦输入 + 落库后轮次级溯源（Source.turns） |
| `skip` + 理由 | 哪几轮**明确不蒸** | "不蒸"成为显式留痕决策，而非悄悄漏掉 |

### 4.6 计划的归档与知识的关联方向【已拍板】

- 计划**持久化**：`data/plans/plan-<yyyymmdd>-<seq>.json`，confirm 后回写 `result`（每项的落库知识 id / skipped）。
- **关联方向 = 计划 → 知识**（计划文件里记录落库结果）；知识侧**不加** plan 字段。
  理由：知识 frontmatter 只放"从哪来"（sources 锚点+轮次，溯源=可信度属性）；
  "当时怎么决策的"是过程档案，归 plans/。反查（知识 → 计划）用 grep 即可，低频。
- **计划的独立价值 = 负知识载体**：skip 决策永久留痕——后续增量补蒸时"这段蒸过吗"有据可查，
  游标抹不掉的"明确不蒸 vs 漏了"之辨由此解决；也是蒸馏质量反馈回路的数据源。
- 红利：计划批准后 parent 已是真实 id，旧流程的 **MAIN 两段式占位 hack 消解**。

## 五、双驱动模式【已拍板】

| | 会话驱动 | 主题驱动 |
|---|---|---|
| 入口 | `mem distill <anchor>` | `mem distill --domain <领域>` |
| 场景 | 维护期：这次对话补了什么 | **建树/补全期**：把这个领域蒸全 |
| 系统供给 | 增量压缩视图 + 命中子树 | 领域树全景（按轴分组）+ 相关锚点清单 + **盘点报告**（各轴已有/空缺） |
| 汇入 | 同一四轮协议（R1 起） | 同一四轮协议（R1 起） |

主题驱动的盘点缺口识别：系统供"已有树全景 + 锚点清单"，AI 粗读锚点产话题地图、对照已有树判断缺口——
缺口判断归模型，素材归系统。（系统配套缺口：锚点当前不进索引无检索能力 → 实施阶段补 TruthStore.search_anchors 子串检索；锚点规模小，暂不上 FTS 表。）

## 六、系统职责（规则代码化：能机械检查的绝不依赖自觉）

### 6.1 系统供给

| 供给 | 服务 | 说明 |
|---|---|---|
| R1 增量视图 | DistillService | 全量优先（正确性）；超预算才压缩（剥 tool_result/截长文），预算可配 |
| 已有子树预检索 | SearchService | 标题包含为主、FTS 短语为辅；补祖先链 + 命中节点的直接子节点，总量可配 |
| 领域盘点报告 | DistillService | 按轴分组的全景 + 各轴覆盖度 |

### 6.2 confirm 硬校验清单【已落地 · 阶段1】

实现见 `application/plan_checker.py`：规则列表模式，每条规则声明**适用模式 × 适用阶段**
（draft = submit 时可跑 / final = confirm 才跑）。submit 跑 draft 级；confirm 跑全部——批准后手改坐标当场拒收。

**通用规则（domain / event 均适用）**

| 级别 | 校验项 | 说明 |
|---|---|---|
| 拒收 | 计划级锚点缺失/不存在（session 驱动） | 游标回写目标 |
| 拒收 | 每项 source.anchor 必填且存在 | skip 也必填——它是"哪几轮不蒸"的载体 |
| 拒收 | edit 项 edit_id 必填且指向存在节点 | |
| 拒收 | create 项 parent 必填且合法 | 存在的节点，或 `$ROOT`（仅新建领域根时可用） |
| 拒收 | 非 skip 项 title 必填 | title 是 R1 定位产物（树节点的名字），不是 R3 正文 |
| 警告 | **轮次覆盖完整性**：items 的 source.turns 并集未覆盖 expected_turns | 治"悄悄漏掉"——显式 skip 计入覆盖 |
| 警告 | 非 skip 项未标注 source.turns | 溯源粒度降级为整段锚点 |
| 警告（final） | 非 skip 项缺 summary/body | R3 完成度 |

**领域模式专属规则**

| 级别 | 校验项 | 说明 |
|---|---|---|
| 拒收 | 领域根声明非法 | existing 必须指向 model 根；create 不得与活跃根重名（治 E2 平行树红线；deprecated 根允许重建） |
| 拒收 | aspect 必填且在值域内 | 值域 config 可配（`distill.aspects`） |
| 警告 | create 项与活跃节点同 title | 提示该 edit 而非新建 |
| 警告 | create 项 aspect 与父节点不一致 | 坐标纠错 |

另有两条靠机制而非规则：**重复提交**——submit 拒绝已带 plan_id 的计划；**批准后篡改**——confirm 重跑全规则集。

### 6.3 反馈回路

计划归档（4.6）为第一块砖；后续可统计：计划批准率、skip 率、计划被改动的坐标分布（= AI 定位能力的度量）。
（另：deprecated 节点当前仍参与检索召回，实施阶段一并修复。）

## 七、内容规范（节点写什么）【提案 · 待拍板】

> 哲学（用户拍板）：**代码是事实，记忆是索引**。落"入口、坐标、为什么"；不落"实现细节"（要细节去读代码）。

### 7.1 三字段分工（保留此分层，与本体系无冲突）

- **title**：一句话断言（对象+动作/结果），2-3 核心检索词，不堆括号细目；
- **summary**：结论先行（第一句=这是什么+什么结论），支撑"只看 summary 判断要不要"；
- **body**：按下表分轴模板；细节关键词/别名进 body（FTS 召回兜底）。

### 7.2 入口索引精确清单（所有轴通用的"代码锚点"标准）

落：**HTTP URL ↔ Controller#method 映射**（外部行为定位代码的桥）、表名/字段、状态枚举、**设计理由**（代码有但读不出"为什么"的，如"分布式锁防并发重复"）。
不落：if/else 级实现细节、局部变量、代码片段。

### 7.3 分轴 body 模板

**流程轴节点**（流程阶段，如"创建需求单流程"）：
```
定位：属于哪个领域哪个环节（一句话）
入口：HTTP URL ↔ Controller#method
步骤：1→2→3（每步：做什么 + 调什么 + 落库点）
分支条件：什么情况走什么分支（如 save=PS / submit=RP）
依据：为什么这样设计
边界：什么情况不走这条路
```

**结构轴节点**（实体/表/状态机）：
```
实体与表：表名 + 职责 + 关键字段 + 关联键（谁挂谁）
状态机：枚举值 + 流转 + 触发条件 + 聚合规则
依据：为什么这么建模
```

**边界轴节点**（外部调用/入口）：
```
调谁/谁调：外部系统 + 接口
解决什么问题：业务目的
调用点：我方发起位置（类#方法）
契约要点：关键出入参
失败与兜底：超时/失败策略
```

**约束轴节点**（规则/坑）：
```
规则：一句话断言
依据：为什么这么定（讨论/事故来源）
触发条件 + 违反后果
代码锚点：校验位置
```

## 九、明确不做

- 事件蒸馏（另立专题）
