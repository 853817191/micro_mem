# 蒸馏提炼规范 · 领域模式（DISTILL_DOMAIN）

> 场景：蒸馏「一个业务领域长什么样」——结构 / 状态机 / 主流程 / 生命周期，主体是**领域**。
> 产出的形状：**一张网**——1 个领域根（model）+ 子节点（parent 纵向）+ 领域间 link（横向）。
> 先读 `DISTILL_GUIDE.md`（共用篇），再读本文档。

## 0. 一句话定位

- **领域 vs 事件**：事件是「发生了一次」，领域是「一直存在的那套规则/结构」。
- 判断：这段内容描述的是「某一次发生了什么」还是「这个业务本身怎么运转」？
  - 后者 → **领域模式（本文档）**。
  - 前者 → 事件模式（DISTILL_EVENT.md）。

## 1. 核心原则：先识领域，再拆子网

- 第一步先回答：这段描述的是**哪个领域**？（一句话：这是什么系统/业务域）
- 立领域根（type=`model`），再往下拆子网。

## 2. 蒸馏结构：领域根 + 子网（一张网）

- **根**：领域根（type=`model`，无 parent），body 写领域总览（定位/边界/主流程一句话）。
- **纵向 `parent`**：领域 → 子领域/模块 → 规则/状态。子领域也是 `model`，规则是 `fact`，流程是 `method`，具体事件是 `event`。
- **横向 `link`**：领域之间调用/流转/依赖（如「需求单领域 → 申请单领域」），有向。

## 3. 领域模板（body 写法，分层）

**L0 领域根 body**：

```
定位：这个领域是什么、管什么、边界在哪
主流程：端到端一句话（起点 → 关键节点 → 终点）
生命周期/状态机：主要状态 + 流转
子领域索引：子领域名 → 各自 parent（一句话职责）
```

**L1 子领域/模块 body**：

```
职责：这个模块干什么
关键规则/状态：约束、校验、状态流转
边：parent（谁包含我）、link（我调用谁 / 谁调用我）
```

**L2 规则/流程节点 body**：

- `fact`：规则原文 + 触发条件 + 违反后果
- `method`：步骤 + 输入输出 + 复用边界
- `event`（领域内有具体事件）：见事件模式

## 4. 递归分层

- 领域可多层：大领域 → 子领域 → 子子领域。每层都是 `model` 挂 `parent`。
- **分层开关 = 独立成模块**：这个子领域能否被独立检索 / 独立演进？
  - 能 → 独立 `model` 节点（挂 parent）
  - 不能 → 并入父 body

## 5. 增量蒸馏（领域如何长出来）

- 一次会话往往只补领域的一小块（一个状态机 / 一条规则 / 一个子流程）。
- 步骤：先 `search` 找已有领域根 → 有则判断新内容挂哪（新子节点 parent 到根/子领域，或 `edit` 已有节点）→ 无则新建根。
- **link 语义**：跨领域调用用 `link`（有向，from 我 → to 我依赖的）。

## 6. few-shot（示例）

**例 A：国际机票需求单领域**（一次会话补齐状态机）

```json
[
  {
    "type": "model", "scope": "domain",
    "title": "国际机票需求单领域",
    "summary": "国际机票需求单的业务领域：从创建、审批、出票到完结的状态机与校验规则。",
    "body": "定位：国际机票需求单全流程管理。\n主流程：创建 → 审批 → 出票 → 完结。\n状态机：草稿/待审/已审/出票中/已出票/完结/驳回。\n子领域：申请单领域（parent）、出票对接（method，parent）。",
    "suggested_parents": [], "suggested_links": ["k-<申请单领域>"],
    "sources": [{"type": "conversation_distilled", "ref": "anchors/s-xxx.md"}],
    "decision": "keep"
  },
  {
    "type": "fact", "scope": "domain",
    "title": "国际机票需求单状态机与校验规则",
    "summary": "需求单状态流转：草稿→待审→已审→出票中→已出票→完结；驳回可回到草稿；各状态转换有校验约束。",
    "body": "状态：草稿/待审/已审/出票中/已出票/完结/驳回。\n流转：草稿→待审→已审→出票中→已出票→完结；驳回→草稿。\n校验：待审必须有乘机人+航班信息；出票前须审核通过。",
    "suggested_parents": ["k-<国际机票需求单领域>"], "suggested_links": [],
    "sources": [{"type": "conversation_distilled", "ref": "anchors/s-xxx.md"}],
    "decision": "keep"
  }
]
```

- 领域根（model，无 parent）→ 规则节点（fact，`suggested_parents` 指向根）→ 跨领域 link（`申请单领域`）。
- 一句话网：根描述「是什么」，parent 描述「属于谁」，link 描述「调用谁」。

**例 B：制造工厂（跨领域）**——采购/制造/销售/物流/售后各自是 `model` 根，之间用 `link` 串成完整业务：

```
采购领域 --link--> 制造领域 --link--> 销售领域 --link--> 物流领域 --link--> 售后领域
```

- 每个领域是独立 `model` 根（各有一套自己的子网），跨领域用 `link` 表达流转/依赖。
- 这验证了四分类的扩展性：新业务进来是**新实例**（新领域根 + 新网），不是新 type。
