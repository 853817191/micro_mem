# 蒸馏提炼规范 · 共用篇（DISTILL_GUIDE）

> 蒸馏规范分三份，分工如下（蒸馏前先读本文档，再按场景选读模式篇）：
> - **SKILL.md**（入口）：命令怎么跑 + 「蒸馏分两种模式，先判断」。
> - **本文档（共用篇）**：所有蒸馏模式**共用**的字段规范、type/scope 判定、去重、候选格式。
> - **DISTILL_EVENT.md**（事件模式）：蒸馏「一次会话做了什么事」——先识事件、过程模板、产树。
> - **DISTILL_DOMAIN.md**（领域模式）：蒸馏「一个业务领域长什么样」——先识领域、领域模板、产网。

## 0. 定位与使用时机

- 触发蒸馏（`anchor` / `distill` / `confirm` 或用户说"帮我蒸馏"）前，**先读完本文档 + 按场景选读一篇模式篇**，再产出候选。
- 本文档是**硬标准**：不达标就调整候选，不要凭感觉产出一批再说。

## 1. 知识类型四分类（type）

- type 表达「**认识论类型 = 回答什么问题**（知识的内容形态）」，四类封闭：

  | type | 值 | 回答 | 例 |
  |---|---|---|---|
  | EVENT | `event` | 发生了什么——一件事的完整过程 | micro_mem 工程化优化 |
  | MODEL | `model` | 这是什么系统/领域——领域模型（结构/状态机/主流程/生命周期） | 国际机票下单业务流程 |
  | FACT | `fact` | 是什么（单条）——一条规则/约束/结论 | FTS5 <3 字返回空 |
  | METHOD | `method` | 怎么办——一套做法/流程 | 出票对接 |

- **判别 MODEL vs FACT**（最易混）：一句话能说完的独立断言 → `FACT`；需要结构/图/状态流转才说得清 → `MODEL`。一句话记：**FACT 是原子，MODEL 是结构。**
- 新业务进来（工厂、电商、金融…）都是这四类的组合，是**新实例**不是**新类型**，除非出现四类都答不了的认识论问题，才考虑加值。

## 2. 主副交给边（角色不由 type 决定）

- **主节点** = 无 `parent` 入边；**挂靠节点** = 有 `parent` 入边。
- 任何 type 都能主能副：EVENT 可以是主（独立事件）也可以是副（子事件挂大事件）；MODEL 可以是主（领域根）也可以是副（子领域挂大领域）。
- **纵向用 `parent`**（从属/包含：根 → 模块 → 规则）；**横向用 `link`**（调用/流转/依赖：领域之间、环节之间）。
- 一句：**type 管「内容是什么」，边管「在网里什么位置」**，两件事各管各的。

## 3. 目标与第一原则

- 蒸馏产出**知识**（不是对话摘录）：锚点保真存档、知识可独立检索、知识之间成网。
- 四条第一原则约束产出：
  1. **检索归系统**：召回靠 body 全文进索引兜底，title 只放核心词、summary 可判断，不靠堆词。
  2. **判断归模型**：summary 带结论信息量（结论先行）。
  3. **锚归原文**：body 保留硬信息（命名/路径/版本/数字），可溯源回对话。
  4. **代码归仓库**：代码才是事实真值。记忆只落「指向代码的锚」（类名/方法/表名/路径），不落实现细节；要细节去读代码，不复制代码片段进 body。

## 4. scope 判定（universal / domain / personal）

- 判据：**换一个项目/团队还成立吗？**
  - 成立 → `universal`（跨项目可复用的通用方法/原则）
  - 只在这个业务域/项目组 → `domain`
  - 纯个人习惯/偏好 → `personal`

## 5. title / summary / body 三字段分工（各管一段，别错位）

记忆给后面 AI 用，走三步：**搜**（关键词搜 title）→ **判**（看 summary 决定要不要）→ **用**（读 body 拿硬信息）。三字段各管一段：

- **title 管「搜得到 + 认得出」**：一句话断言（`对象 + 动作/结果`），只放 2-3 个核心检索词，**不堆括号细目**。反模式：`xxx 优化（A/B/C/D/E/F）`。自检：删掉括号还能一句话说清吗？
- **summary 管「判得准」**：结论先行（见第 6 章）。
- **body 管「用得上 + 召回兜底」**（见第 7 章）。

## 6. summary 规范（判断字段，重中之重）

- **结论先行**：第一句必须是结论——「这是什么 + 解决了什么/得出什么结论」。
- **三段结构**：① 结论（一句话）→ ② 要点（关键做法，1-2 句）→ ③ 约束/结果（复用边界或最终结果）。
- 原则不变：检索后**只看 summary** 就能判断「是不是用户要找的那件事」。
- 反模式：`我们讨论了 XX`（只有动作，无结论）；描述结构当开头、结论藏到结尾。
- 自检：遮住 body，只看 summary，能说出「解决了什么问题」吗？不能 → 缺结论，重写。

## 7. body 规范（复用字段 + 召回兜底）

- body 的目标：**未来复用者不看原文就能用**。四段结构各管一段：
  1. **结论**：这是什么 / 解决了什么（一句话断言）
  2. **依据**：为什么成立——讨论里暴露的关键论据、反对意见、最终拍板理由（**蒸馏提炼，不是抄对话原文**）
  3. **边界**：什么条件下不成立、什么时候该推翻 / 演进
  4. **硬信息**：命名、路径、版本号、数字、命令、需求单号、commit（**一个不丢**）
- **过程原文不落 body**：逐字对话流水归锚点（`sources` 溯源），body 只落「蒸馏后的结论 + 依据 + 边界」。抄原文进 body = 两处真值 + 检索噪音。
- body 的具体模板见各模式篇（事件篇：过程模板；领域篇：领域模板）。
- 保留可溯源锚（如 TCX-66155、文件路径），保证「锚归原文」。
- **body 是召回兜底层**：所有细节关键词（含 title/summary 没写的别名、缩写、易搜词）都放 body——body 已进 FTS 索引，「关键词只在 body」也能搜到，不漏。

## 8. 去重与聚合

- **提炼前先 `search`** 已有知识，判三类：
  1. 已有同类且信息重叠 → **edit 更新已有**（不新建）；
  2. 已有上位主题 → **挂靠**（`suggested_parents`）；
  3. 全新 → 新建。
- 特别地：先 search 判断「这件事/领域是不是已有节点的延续」——是则 edit/挂靠到已有节点，而不是新建平行节点。
- 目标：同一主题不散落、不重复。

## 9. sources 与候选 JSON 格式

- `sources.ref` 必须指向**真实锚点 id**（否则 confirm 溯源校验拒收）。
- 字段与代码对齐：`type/scope/title/summary/body/suggested_parents/suggested_links/sources/decision`。
- `decision` 取值：`keep`（新建/保留）、`edit`（更新已有，需带 `edit_id`）、`reject`（不要）。

## 10. 负例清单（共用）

- 闲聊、寒暄、一次性问答、纯操作过程（无结论）、**决策未定的中间态**、情绪/吐槽。
- **只蒸实现细节、漏掉主体事件/领域**（丢主节点，详见各模式篇反例）。

- [ ] summary 结论先行？（第一句是结论，不是描述/背景）
- [ ] 遮住 body 只看 summary，能说出「解决了什么」？
- [ ] title 一句话断言、只 2-3 核心词（删括号还能说清）？
- [ ] body 四段齐全？（结论 + 依据 + 边界 + 硬信息；依据是蒸馏提炼的，没抄对话原文）
- [ ] body 兜底召回完整？（细节关键词/别名/缩写都在 body；硬信息命名/路径/版本/数字不丢）
