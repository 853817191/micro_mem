# 蒸馏提炼规范 · 领域模式（DISTILL_DOMAIN）

> 场景：蒸馏「一个业务领域长什么样」——结构 / 状态机 / 主流程 / 生命周期，主体是**领域**。
> 产出的形状：**一张网**——1 个领域根（model）+ 子节点（parent 纵向）+ 领域间 link（横向）。
> 先读 `DISTILL_GUIDE.md`（共用篇），再读本文档。

## 0. 一句话定位

- **领域 vs 事件**：事件是「发生了一次」，领域是「一直存在的那套规则/结构」。
- 判断：这段内容描述的是「某一次发生了什么」还是「这个业务本身怎么运转」？
  - 后者 → **领域模式（本文档）**。
  - 前者 → 事件模式（DISTILL_EVENT.md）。

## 1. 核心原则：先识领域，再拆子网

- 第一步先回答：这段描述的是**哪个领域**？（一句话：这是什么系统/业务域）
- 立领域根（type=`model`），再往下拆子网。

## 2. 蒸馏结构：领域根 + 子网（一张网）

- **根**：领域根（type=`model`，无 parent），body 写领域总览（定位/边界/主流程一句话）。
- **纵向 `parent`**：领域 → 子领域/模块 → 规则/状态。子领域也是 `model`，规则是 `fact`，流程是 `method`，具体事件是 `event`。
- **横向 `link`**：领域之间调用/流转/依赖（如「需求单领域 → 申请单领域」），有向。

## 3. 领域骨架（body 写法 · 分层模板）

> 骨架 = 领域节点 body 的写作模板 + 拆子网的依据。
> **代码是事实源，骨架是导航层**：骨架记「结构 + 为什么」，不复制代码事实，只落指向代码的锚点。

### 3.1 代码信息三档（所有代码相关维度都按这个停）

| 档 | 内容 | 落不落 |
|---|---|---|
| **S1 结构锚点** | 接口名·职责·签名、调用链、表名·字段、状态流转 | ✅ 落（stable）|
| **S2 业务约束** | 校验规则、关键决策、踩的坑、命名语义、落库点 | ✅ 落（evolving，变了 edit）|
| **S3 实现细节** | if/else、局部变量、代码片段 | ❌ 不落（按锚点去读代码）|

- 一句：**记忆只记代码里读不到的东西**——S1 是「定位代码的坐标」，S2 是「代码没写出来的为什么」，S3 是「代码里能直接读到的」，所以 S3 不落。

### 3.2 骨架树（分层 · 必选/可选）

```
MODEL 骨架
├─ 0 定位层（必选）
│    ├─ 定位：什么领域、管什么、边界
│    └─ 主流程一句话：起点 → 关键节点 → 终点
├─ 1 结构层（必选）
│    ├─ 实体：名称 + 职责 + 表锚点(S1) + 关键字段(S1)
│    ├─ 表·字段：表名 + 关键字段(S1)
│    └─ 枚举·常量：状态/类型枚举(S1)
├─ 2 行为层（必选）
│    ├─ 状态机：状态 + 流转 + 触发条件(S1/S2)
│    ├─ 主流程：端到端链路，接口编排(S1 → evolving)
│    ├─ 接口：名称 + 职责 + 签名(S1) + 落库点(S2)
│    └─ 关键锚点与易错点：落库点 / 易踩坑(S2)   ← 不落实现细节
├─ 3 约束层（必选）
│    ├─ 校验规则：约束 + 触发条件 + 违反后果(S2)
│    └─ 边界·异常：失败 / 回退 / 兜底(S2)
├─ 4 耦合层（必选）← 评估影响的根基
│    ├─ 调用链：接口 A → 接口 B(S1 → evolving)
│    ├─ 读写关系：谁读写哪张表(S1)
│    └─ 状态耦合：改状态影响哪些校验/流转(S2)
├─ 5 集成层（可选）
│    └─ 角色 / 权限 / 上下游依赖 / 消息事件 / 定时任务 / 配置 / 查询
└─ 6 子领域（递归）—— 每个子领域 = 一个 model 节点，套同一骨架
```

### 3.3 骨架一鱼两吃（同时管根 body + 拆子网）

| 维度 | 领域根 body 写什么 | 拆什么子节点 |
|---|---|---|
| 定位 / 主流程 | 一句话 | 不拆 |
| 实体 / 表 / 枚举 | 清单 + 锚点(S1) | 复杂实体拆 fact |
| 状态机 | 状态总览 | 拆 **fact** |
| 接口 | 接口清单(S1) | 拆 **method** |
| 耦合 | 调用链 / 读写关系总览 | 并入接口 method / 单独 fact |
| 子领域 | 子领域索引 | 拆 **model** |

### 3.4 子节点 body 模板（按 type 选型）

- `fact`：规则原文 + 依据（为什么这么定）+ 触发条件 + 违反后果
- `method`：步骤 + 依据（为什么这么做）+ 输入输出 + 复用边界
- `event`（领域内有具体事件）：见事件模式

## 4. 递归分层

- 领域可多层：大领域 → 子领域 → 子子领域。每层都是 `model` 挂 `parent`。
- **分层开关 = 独立成模块**：这个子领域能否被独立检索 / 独立演进？
  - 能 → 独立 `model` 节点（挂 parent）
  - 不能 → 并入父 body

## 5. 增量蒸馏（领域如何长出来）

- 一次会话往往只补领域的一小块（一个状态机 / 一条规则 / 一个子流程）。
- 步骤：先 `search` 找已有领域根 → 有则判断新内容挂哪（新子节点 parent 到根/子领域，或 `edit` 已有节点）→ 无则新建根。
- **link 语义**：跨领域调用用 `link`（有向，from 我 → to 我依赖的）。

## 6. few-shot（示例）

**例 A：国际机票需求单领域**（一次会话补齐状态机）

```json
[
  {
    "type": "model", "scope": "domain",
    "title": "国际机票需求单领域",
    "summary": "国际机票需求单的业务领域：从创建、审批、出票到完结的状态机与校验规则。",
    "body": "定位：国际机票需求单全流程管理，边界=从创建到完结。\n主流程：创建 → 审批 → 出票 → 完结。\n状态机(S1/S2)：草稿/待审/已审/出票中/已出票/完结/驳回；驳回→草稿。\n实体(S1)：需求单 Demand、乘机人 Passenger、航班 Flight。\n表(S1)：demand / demand_passenger。\n接口(S1)：DemandController.create / DemandService.approve / IssueService.issue。\n校验(S2)：待审必须有乘机人+航班；出票前须审核通过。\n子领域：申请单领域（parent）、出票对接（method，parent）。",
    "suggested_parents": [], "suggested_links": ["k-<申请单领域>"],
    "sources": [{"type": "conversation_distilled", "ref": "anchors/s-xxx.md"}],
    "decision": "keep"
  },
  {
    "type": "fact", "scope": "domain",
    "title": "国际机票需求单状态机与校验规则",
    "summary": "需求单状态流转：草稿→待审→已审→出票中→已出票→完结；驳回可回到草稿；各状态转换有校验约束。",
    "body": "状态：草稿/待审/已审/出票中/已出票/完结/驳回。\n流转：草稿→待审→已审→出票中→已出票→完结；驳回→草稿。\n校验：待审必须有乘机人+航班信息；出票前须审核通过。",
    "suggested_parents": ["k-<国际机票需求单领域>"], "suggested_links": [],
    "sources": [{"type": "conversation_distilled", "ref": "anchors/s-xxx.md"}],
    "decision": "keep"

```

- 领域根（model，无 parent）→ 规则节点（fact，`suggested_parents` 指向根）→ 跨领域 link（`申请单领域`）。
- 一句话网：根描述「是什么」，parent 描述「属于谁」，link 描述「调用谁」。
- body 里的 S1 代码锚点（`DemandController.create` / 表 `demand`）是**示意**，实际蒸馏时按真实代码填；S3 实现细节不落 body。

**例 B：制造工厂（跨领域）**——采购/制造/销售/物流/售后各自是 `model` 根，之间用 `link` 串成完整业务：

```
采购领域 --link--> 制造领域 --link--> 销售领域 --link--> 物流领域 --link--> 售后领域
```

- 每个领域是独立 `model` 根（各有一套自己的子网），跨领域用 `link` 表达流转/依赖。
- 这验证了四分类的扩展性：新业务进来是**新实例**（新领域根 + 新网），不是新 type。
